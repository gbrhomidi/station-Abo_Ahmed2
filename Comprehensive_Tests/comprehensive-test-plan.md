# الخطة الشاملة لاختبار مشروع محطة الوقود وإدارة الأعمال

**النطاق:** تطبيق Android مبني بـKotlin، يستخدم SQLite محلياً، ويضم واجهات HTML/JavaScript داخل Android WebView مع Android Bridge. تظهر البنية المتاحة أن المشروع يتضمن وحدات مالية ومبيعات ونقاط بيع ومخزون وديون عملاء ومركبات ووقود ورسائل SMS وتقارير ونسخاً احتياطية، إضافة إلى ملفات أصول محلية وشاشات ويب كثيرة.

> هذه وثيقة تخطيط واختبارات مقترحة، وليست تقريراً عن تنفيذها. لم تُشغّل هذه الاختبارات في هذه الخطوة، ولم يتم تعديل التطبيق أو إجراء أي تغيير أو دفع على GitHub. المعاينة السابقة للبنية لم تكن جرداً كاملاً لكل إعدادات Gradle أو CI؛ لذلك افحص أسماء المهام والإصدارات الفعلية في المشروع قبل اعتماد الأوامر الاختيارية.

## 1. الغاية ومبادئ الاختبار

تهدف الخطة إلى حماية صحة العمليات المالية والمخزنية، موثوقية بيانات SQLite، سلامة العزل بين المحطات والمستخدمين، توافق واجهات الويب مع Android Bridge، واستقرار التطبيق على الأجهزة الحقيقية. لا ينبغي أن يقتصر التحقق على أن الشاشة «تفتح»؛ بل يجب إثبات صحة البيانات قبل العملية وبعدها، واتساق الأرصدة والمجاميع، وسلامة الفشل والتراجع، وعدم تأثر الوظائف غير الداخلة في التغيير.

مبادئ أساسية:

1. **اختبار مبني على المخاطر:** الأولوية للمدفوعات، القيود المالية، المبيعات، المخزون، النسخ والاستعادة، صلاحيات المستخدمين، والعزل بين المحطات.
2. **عدم استعمال بيانات إنتاج:** الاختبار على قاعدة معزولة وبيانات اصطناعية؛ لا تنفذ اختبارات كتابة أو حذف أو استعادة على بيانات العملاء الحقيقية.
3. **اختبارات قابلة للتكرار:** ساعة ثابتة، بيانات seed، معرفات واضحة، وتهيئة وتنظيف مضمونان.
4. **اختبار النتيجة لا الواجهة فقط:** تحقق من رسالة الواجهة، نتيجة Bridge، صفوف SQLite، الرصيد/الرصيد المتبقي، السجل، والتقرير الناتج.
5. **منع النجاح الكاذب:** لا تجعل الاختبارات تتخطى الأخطاء أو تتجاهل null/timeout أو تعتمد على ترتيب غير مضمون.
6. **تغطية مسارات النجاح والفشل والحدود والتزامن:** كل عملية حرجة لها حالات صحيحة، مرفوضة، متكررة، متزامنة، وبعد الانقطاع.
7. **عدم فرض تغيير وظيفي عبر الاختبار:** الاختبار يوثق القواعد الحالية المعتمدة؛ إذا كانت قاعدة العمل غير محددة، يسجل القرار المطلوب قبل كتابة assertion.

## 2. طبقات الاختبار وأنواعها

### 2.1 اختبارات الوحدة Unit
اختبار دوال أو كائنات صغيرة بمعزل عن Android وSQLite الحقيقيين، مع بدائل للساعة، المستودع، SMS، الشبكة، والملفات.

مجالات مناسبة بحسب البنية الظاهرة:
- `BusinessDay`: حدود اليوم التجاري، تبدل التاريخ والمنطقة الزمنية، توقيت بدء/إقفال اليوم.
- `QueryUtils`: بناء شروط واستعلامات آمنة، حدود pagination، الفرز، المعاملات الفارغة.
- `SecurityValidator`: مدخلات صالحة وغير صالحة، طول الحقول، أحرف خاصة، حدود الأرقام.
- `FinancialIntegrityAuditor`: قواعد كشف عدم الاتزان، الأرصدة غير المتطابقة، السجلات اليتيمة، وإخراج نتائج قابلة للتفسير.
- `BankMessageParser` و`BankPaymentMatchingEngine` و`BankSmsVerificationEngine`: تحليل رسائل متنوعة، التطابق، الثقة، منع التكرار، والحالات الغامضة.
- `SettingsValidator`، المحولات، `ApplicationSettingsMapper` ومكونات الإعدادات.
- حسابات المبالغ والخصومات والضرائب والفروقات والتقريب.

### 2.2 اختبارات التكامل Integration
تختبر تعاون طبقتين أو أكثر: Repository/DAO مع SQLite، عامل مع قاعدة البيانات، HTML مع Bridge، إعدادات مع التخزين، أو parser مع محرك المطابقة. تستعمل قاعدة مؤقتة أو fake مضبوطاً بدلاً من بيانات حقيقية.

### 2.3 اختبارات المكونات Android Component
اختبار `Activity` و`Service` و`Worker` و`Receiver` والسلوك عند lifecycle، الأذونات، إعادة إنشاء الشاشة، تشغيل الخلفية، وإيقاف النظام. استخدم AndroidX Test وEspresso عند توفرهما وإعدادهما.

### 2.4 اختبارات واجهة المستخدم UI/E2E
تحاكي رحلة مستخدم كاملة من الشاشة إلى حفظ البيانات ثم الرجوع وقراءة الناتج. أمثلة: فتح عميل، إضافة دفعة، تحقق الرصيد وسجل الحركة؛ إنشاء بيع، تحقق الإيصال والمخزون والصندوق؛ فتح تقرير، تطبيق مرشحات، ثم تصدير.

### 2.5 اختبارات قبول الأعمال UAT
ينفذها مالك المنتج/المحاسب/المستخدم النهائي على سيناريوهات معتمدة تمثل سير العمل الفعلي، مع مطابقة المخرجات المحاسبية والتقارير مع expected results مكتوبة مسبقاً.

### 2.6 اختبارات الانحدار Regression
إعادة تشغيل مجموعة الاختبارات ذات الصلة بعد كل تغيير، مع اختبار صريح للوظائف المجاورة التي قد تتأثر. في تغييرات شاشة ديون العملاء مثلاً: الدفع، حساب الرصيد، الصندوق/البنك، سجل العميل، تقارير الديون، عرض القائمة، الصلاحيات، والتنقل.

### 2.7 اختبارات الاستكشاف Exploratory
جلسات منظمة دون مسارات ثابتة مسبقاً لاكتشاف سلوك غير متوقع. يسجل المختبر الإصدار والجهاز والبيانات والخطوات والنتيجة المتوقعة والفعلية والدليل.

## 4. الاختبارات الوظيفية التفصيلية حسب المجال

### 4.1 ديون العملاء والدفعات
- إضافة دفعة نقدية بصندوق تحصيل صالح، ودفعة عبر حساب بنكي صالح، والتأكد من رفض تحديد الاثنين معاً أو عدم تحديد أي منهما إذا كانت قاعدة العمل تشترط واحداً فقط.
- قيم الدفعة: أقل من الدين، مساوية له، أكبر منه، صفر، سالبة، فارغة، قيمة عشرية طويلة، أكبر حد مدعوم.
- التحقق من الرصيد السابق + الدفعة = الرصيد الجديد حسب تعريف النظام، ومن عدم تجاوز السداد للدين إلا إذا كان مسموحاً كرصيد دائن.
- تحقق ذريّة العملية: إما تسجيل الدفعة وكل آثارها (حركة نقدية/بنكية، سجل العميل، إيصال) معاً أو عدم تسجيل أي منها عند الفشل.
- ضغط زر الحفظ عدة مرات، إعادة إرسال الطلب، النقر السريع، أو إعادة فتح الشاشة: لا تنشأ دفعات مكررة؛ استخدم معرف idempotency إن كان النظام يدعمه.
- إغلاق المودال أو رجوع المستخدم أثناء الإرسال؛ انقطاع التطبيق بعد الحفظ وقبل تحديث الواجهة؛ إعادة فتح الشاشة تعرض المصدر المحفوظ فعلياً.
- تاريخ الدفع، تاريخ الاستحقاق، المنطقة الزمنية، ترتيب سجل الحركات، حدود اليوم التجاري.
- تفاصيل العميل والسجل: عميل موجود/محذوف/غير مخول، بلا معاملات/معاملات كثيرة، دفعات مرتجعة/ملغاة، التنقل رجوعاً من المودال.
- فلاتر تقارير الديون: عميل، حالة الدين، فترة، متأخر/غير متأخر، صندوق/بنك، الفرع/المحطة؛ تحقق من تطابق مجموع النتائج مع التفاصيل.
- عرض جدول/بطاقات/شجرة: نفس البيانات والترتيب والصلاحيات؛ حالة فارغة، أحجام كبيرة، تبديل العرض مع البحث/الترشيح.
- الخصوصية والصلاحيات: المستخدم الذي لا يملك صلاحية الدفع أو رؤية عميل محطة أخرى لا يمكنه الوصول عبر الواجهة أو استدعاء Bridge مباشرة.

**حالات حافة مالية:** تقريب العملة، تغير إعداد الدقة، سداد جزئي متزامن من مستخدمين، تعديل الدين أثناء الدفع، دفعة بتاريخ سابق، تغير الصندوق أو تعطيله، سجل غير متوازن، فقد سجل مرتبط.

### 4.2 نقاط البيع والمبيعات والخصومات
- بيع نقدي، بنكي، آجل، ومزيج وسائل الدفع حسب القواعد المسموح بها.
- الكمية صفر/سالبة/أكبر من المخزون، منتج متوقف، سعر غير موجود، خصم ثابت/نسبي، حد الخصم ودور المستخدم.
- اختبار حساب الإجمالي والخصم والضريبة والتقريب والإجمالي المستحق؛ لا تسمح بتجاوزات بسبب التلاعب بالواجهة.
- إلغاء البيع قبل/بعد الحفظ، إرجاع كامل/جزئي، إعادة طباعة الإيصال، تكرار زر الإنهاء، انقطاع في منتصف البيع.
- مطابقة الصفقة مع حركة المخزون والصندوق والقيود والسجل والتقرير، دون ازدواج أو نقص.
- جلسات البيع، إقفال الوردية، إعادة فتحها حسب الصلاحية، فرق النقدية، العمل دون اتصال إن كان مدعوماً.

### 4.3 المحاسبة والصناديق والبنوك
- إدخال/ترحيل قيد متوازن، رفض قيد غير متوازن، منع التعديل بعد الإقفال أو توثيق أثره وفق الصلاحية.
- تحويل بين صندوقين/حسابين: خصم من المصدر وإضافة إلى الوجهة ضمن معاملة ذرية.
- أرصدة افتتاحية، فترات مالية، إقفال يوم/شهر، إلغاء وعكس القيد، ترقيم المستندات وعدم التكرار.
- مطابقة دفتر الأستاذ، الميزانية، التقارير، رصيد الصندوق، وحركة البنك مع مصدر المعاملة.
- فترات فارغة، تاريخ حدود السنة، إعدادات العملة، القيود اليتيمة، الأرصدة السالبة المسموح بها وغير المسموح بها.

### 4.4 المخزون والمستودعات والمشتريات
- استلام/صرف/تحويل/جرد/تسوية/تالف/مرتجع، مع حساب صحيح للكمية والتكلفة.
- لا تصبح الحركة مرئية جزئياً عند فشل أحد أطراف العملية.
- مستويات إعادة الطلب، وحدود المخزون، أكثر من مستودع، منتج له وحدات تحويل.
- عرض تفاصيل حركة خارج الصفحة الحالية، pagination، الترتيب، الفلاتر، وعدم تسرب بيانات مستودع/محطة أخرى.
- التزامن بين بيعين على آخر كمية؛ لا ينتج مخزون سالب إلا إن كانت القاعدة تسمح بذلك صراحة.

### 4.5 الوقود والخزانات والمضخات والقراءات
- قراءات العداد السابقة واللاحقة، التفاف العداد، قراءة أقل من السابقة، كمية سالبة/غير منطقية.
- مطابقة المبيعات مع المضخات والخزانات وعمليات التوريد والفروقات والتسويات.
- تحويلات الوحدات والدقة، حرارة/كثافة إن كانت ممثلة، اختلاف التوقيت/الوردية.
- حدود التنبيه، دقة التقرير، تناسق إجماليات المضخات مع إجمالي الوردية والصندوق.

### 4.6 العملاء والموردون والمركبات والموظفون
- تحقق الحقول المطلوبة، هوية/هاتف مكرر، بحث عربي/لاتيني، حفظ وتعديل وتعطيل دون محو السجل التاريخي.
- المركبات: المستندات، التسجيل، السائق، المصروفات، التتبع؛ صلاحية الصور والملفات والمراجع بعد إعادة فتح النموذج.
- الموظفون والرواتب/المدفوعات: قواعد الاستحقاق والخصم، الفترات، الصلاحيات، توافق الإجمالي مع القيود.

### 4.7 التقارير والتصدير والطباعة
- تقرير فترة تشمل البداية والنهاية، حدود منتصف الليل، منطقة زمنية، وترشيحات متعددة معاً.
- مطابقة مجموع التقرير مع البيانات التفصيلية ومصدر الحقيقة، وتحديد واضح للمرشحات والتاريخ والعملة.
- تصدير PDF/Excel/CSV: ترميز العربية واتجاه RTL، عناوين الأعمدة، الأرقام العشرية، أسماء الملفات، صفحات متعددة، ورقة فارغة، بيانات كبيرة.
- الطباعة/المشاركة، انقطاع الإعداد، تجنب تسريب مسار الملف أو بيانات غير مسموح بها.
- عدم اعتماد التقرير على بيانات cache قديمة بعد حفظ عملية جديدة أو بعد مزامنة/استعادة.

### 4.8 الرسائل النصية والإشعارات والمهام الخلفية
- تحليل رسائل مصرفية سليمة/مشوهة/بلغات وأشكال أرقام مختلفة؛ رسائل متعددة داخل النص؛ مبالغ أو أرقام مرجعية ملتبسة.
- عدم تسجيل دفعة آلياً بسبب مجرد نص متشابه؛ اختبر حدود الثقة وموافقة المستخدم وقابلية التدقيق وفق قواعد المنتج.
- كشف الرسالة المكررة، الرسائل بترتيب متأخر، اختلاف الوقت والتوقيت الصيفي، إذن SMS مرفوض أو غير متاح.
- جدولة تذكير دين؛ إلغاء عند السداد، منع رسائل مكررة، استعادة الجدولة بعد إعادة التشغيل، احترام عدم الإزعاج والصلاحية.
- فشل خدمة/شبكة، إعادة المحاولة بحدود، عدم حجب الخيط الرئيسي، تسجيل آمن دون نصوص حساسة كاملة.

### 4.9 إعدادات ونسخ احتياطي واستعادة
- تغيير الإعدادات، حفظها، قتل التطبيق وإعادة تشغيله، التحقق من persistence والتراجع عن القيم غير الصالحة.
- نسخة احتياطية صحيحة/تالفة/قديمة/من إصدار قاعدة سابق؛ كلمة مرور خاطئة/ملف ناقص/مساحة غير كافية.
- استعادة على قاعدة اختبار: عدد السجلات، العلاقات، الأرصدة، المرفقات، المستخدمين والإعدادات؛ تحقق قبل وبعد الاستعادة.
- ترقية مخطط البيانات migrations من كل إصدار مدعوم، downgrade إذا كان مدعوماً، وفشل migration دون إفساد البيانات.
- عدم تضمين الأسرار أو ملفات غير لازمة في النسخة، وضبط الوصول للملفات المؤقتة.

## 5. اختبارات SQLite وجودة البيانات

1. **المخطط والقيود:** المفاتيح الأساسية والخارجية، NOT NULL، UNIQUE، CHECK والفهارس. حاول إدخال بيانات غير صالحة مباشرة على قاعدة اختبار وتأكد من رفضها.
2. **المعاملات Transactions:** فشل منتصف عملية مالية يؤدي إلى rollback كامل؛ لا تُترك سجلات ناقصة.
3. **العلاقات:** حذف/تعطيل عميل أو صنف لا يطمس التاريخ المالي؛ سياسة cascade/restrict موثقة ومختبرة.
4. **الترحيل Migration:** قاعدة فارغة، كل schema version سابق، قاعدة بيانات كبيرة، أعمدة nullable، بيانات legacy ناقصة، عملية ترقية تقطع ثم تعاد.
5. **التزامن:** كتابتان على السجل نفسه، قراءات متزامنة مع تحديث، قفل قاعدة البيانات، retry آمن، عدم فقد تحديثات.
6. **الاستعلامات:** SQL injection عبر البحث والفرز؛ الاستعلامات ذات المعاملات؛ pagination بلا فجوات أو تكرار عند تغير البيانات.
7. **التناسق:** فحوصات orphan rows، totals، أرصدة سالبة، قيد مالي غير متوازن، اختلاف الإجماليات بين الشاشة والتقرير.
8. **الاستعادة والتلف:** قاعدة مغلقة/مقفلة، مساحة ممتلئة، تلف نسخة، انقطاع طاقة؛ رسائل خطأ مفهومة وعدم تدهور صامت.
9. **العزل:** كل query وعمليات الكتابة تقيد `station_id`/tenant حسب بنية المشروع؛ اختبار IDOR عبر تبديل معرف سجل في طلب Bridge.
10. **الأداء:** explain query plan، فهرس للأعمدة المستخدمة في الفلاتر والربط، تجنب تحميل كامل الجداول في الذاكرة.

## 6. اختبارات WebView وAndroid Bridge

- وجود callback والاسم والتوقيع المتفق عليه بين JavaScript وKotlin، أنواع الوسائط، ترميز JSON والأسماء.
- `requestId` فريد؛ استجابات خارج الترتيب؛ callback غير موجود/مكرر؛ timeout؛ exception؛ إغلاق الشاشة أثناء طلب.
- نجاح/فشل/null/JSON غير صالح/رسالة خطأ، مع استعادة حالة الواجهة وإنهاء spinner دائماً.
- منع استدعاء عمليات قاعدة البيانات الثقيلة على UI thread؛ اختبار threading وسلاسة التفاعل.
- التحقق من جميع المدخلات القادمة من JavaScript داخل Kotlin، وعدم الثقة بواجهة الويب أو إخفاء زر وحده كإجراء صلاحية.
- origin/مصدر المحتوى: عدم إتاحة Bridge لمحتوى غير موثوق أو رابط خارجي؛ منع واجهات JavaScript غير المطلوبة؛ التحقق من إعدادات file access وnavigation حسب الحاجة.
- دورة حياة WebView: إعادة التحميل، تدوير الشاشة، الرجوع، فتح وإغلاق المودال، انتهاء النشاط، تغيير الاتصال.
- HTML/JS syntax، عناصر DOM المطلوبة، رسائل console وأخطاء runtime، أصول offline، service worker/cache عند استخدامه.
- اختبار عربي RTL، لوحة المفاتيح، focus، منع إدخال HTML/JS ضار في بيانات العميل، وescaping عند بناء DOM.
- اختبار callbacks الخاصة بالعملاء والديون والحركات والتقارير بمطابقة schema الفعلي في Kotlin لا أسماء تقريبية.

## 7. اختبارات غير وظيفية

### الأداء والتحمل
- زمن بدء التطبيق وفتح الشاشات، أول عرض للبيانات، البحث، الحفظ، التقرير، التصدير.
- أحجام بيانات ممثلة ثم كبيرة (مثلاً آلاف العملاء/مئات آلاف الحركات) مع تحديد dataset هدف واقعي قبل الاختبار.
- استهلاك CPU/RAM والذاكرة بعد التنقل المتكرر؛ تسرب Activity/WebView/Listeners/bitmaps.
- اختبارات soak: تشغيل متواصل وتكرار عمليات CRUD والتقارير ومزامنة الخلفية؛ نمو قاعدة البيانات والذاكرة.
- اختبارات stress للتزامن والضغط على الصفحات والبحث؛ قياس زمن الانتظار وسلامة البيانات، لا الأداء فقط.
- أداء بدء قاعدة البيانات وmigration والنسخ والاستعادة؛ تأكد أنها لا تحجب الواجهة.

### الأمان والخصوصية
- نموذج تهديد: جهاز مفقود، مستخدم غير مخول، WebView محقون، نسخة احتياطية مسربة، سجل مالي معدل.
- مصادقة وتفويض على كل مسار حساس، بما في ذلك Bridge والمستودع وقاعدة البيانات.
- حقن SQL وHTML/JavaScript، XSS داخل WebView، IDOR، تجاوز صلاحية الصندوق أو محطة أخرى.
- التخزين المحلي: حماية الأسرار والرموز، عدم تسجيل كلمات المرور أو محتوى SMS أو بيانات الدفع الحساسة.
- أذونات Android: أقل صلاحيات لازمة، سلوك رفض الإذن وسحبه بعد المنح.
- التحقق من TLS والاتصالات الخارجية إن وجدت، إعدادات release لا تترك debug/واجهات تشخيص مكشوفة.
- تحليل dependencies والثغرات عبر أدوات ملائمة مثل Gradle dependency verification/SCA أو OWASP Dependency-Check حسب سياسة المشروع.
- اختبار العبث بملف DB/backup والملفات الوسيطة، وطرق تصديرها ومشاركتها.

### التوافق وإمكانية الوصول
- أقل/أعلى Android SDK مستهدف، شاشات صغيرة وكبيرة، كثافات ودقات واتجاه portrait/landscape.
- أجهزة ضعيفة الذاكرة، إصدارات WebView مختلفة، عدم توفر شبكة، لغة عربية وإنجليزية.
- تكبير الخط، قارئ الشاشة، ترتيب التركيز، contrast، أهداف لمس مناسبة، وصف الأيقونات، رسائل أخطاء مفهومة.
- تدوير الشاشة، الوضع الداكن إن مدعوم، لوحة المفاتيح، system back، إغلاق التطبيق واستعادته.

### الاعتمادية والتعافي
- قتل العملية أثناء القراءة والكتابة، إعادة تشغيل الجهاز، مساحة منخفضة، قاعدة مشغولة، إلغاء coroutine.
- فقد شبكة أو DNS أو خدمة SMS، تأخر استجابة Bridge، انتهاء صلاحية الجلسة.
- retry لا يكرر الدفع/البيع؛ استعادة آمنة للحالة، تسجيل تشخيصي لا يكشف أسراراً.
- اختبار التثبيت والتحديث فوق إصدار سابق مع بقاء البيانات، وإزالة/إعادة تثبيت حسب سياسة الاحتفاظ.

### قابلية الصيانة والجودة الساكنة
- compile/lint، تحذيرات Kotlin، فحوصات JavaScript وHTML، تنسيق، فحص أسرار، قواعد lint للـSQL والمراجع غير المستخدمة.
- مراجعة تغييرات schema وAPI وBridge، تحليل التعقيد والتكرار في العمليات الحساسة، وتتبع أخطاء TODO وdeprecated.
- اختبارات contract بين HTML وKotlin وSQLite، اختبارات mutation اختيارية لكشف assertions الضعيفة.

## 8. اختبارات مالية وبيانات متقدمة

- **التقريب:** 0.01، نصف سنت، أعداد كبيرة، تحويل عملة، rounding half-up/half-even وفق القاعدة المعتمدة.
- **الثوابت المحاسبية:** مجموع المدين = مجموع الدائن؛ كل حركة صرف/إضافة تقابل الطرف المقابل؛ مجموع دفعات العميل يطابق حركة الصندوق/البنك.
- **الاستقلالية:** إعادة حساب الرصيد من سجل العمليات يعطي نفس الرصيد المخزن؛ اختبار reconciliation دوري.
- **التكرار:** نفس الطلب مرتين، إعادة محاولة الشبكة، رسالة بنك مكررة، ضغط المستخدم، تشغيل Worker مجدداً.
- **التسلسل الزمني:** وقت جهاز خاطئ، منطقة زمنية، انتقال اليوم التجاري، تواريخ مستقبلية/سابقة، ترتيب إدخال يختلف عن ترتيب التاريخ.
- **التزامن:** مستخدمان يدفعان الدين ذاته، بيعان على المخزون نفسه، إقفال وردية أثناء حفظ حركة.
- **البيانات القديمة:** سجل بلا مرجع، اسم عميل فارغ، عمود جديد null، ترميز عربي قديم، وحدات قياس legacy.
- **الخصوصية:** عدم ظهور بيانات العميل في سجل النظام/الإشعار/رسالة الخطأ/اسم ملف مؤقت بلا ضرورة.

## 9. أمثلة لحالات قبول حرجة مكتوبة

استخدم صيغة Given/When/Then، واستبدل القواعد غير الموثقة بقرار عمل معتمد:

### دفع دين بصندوق التحصيل
- **Given:** عميل لديه دين نشط 100، وصندوق متاح للمستخدم، وقاعدة تسمح باختيار صندوق واحد.
- **When:** يسجل المستخدم دفعة 30 ويؤكدها مرة واحدة.
- **Then:** تنجح العملية مرة واحدة، ينخفض المستحق إلى 70 وفق قواعد النظام، تظهر الحركة في سجل العميل والصندوق، ويعرض التقرير القيم نفسها بعد إعادة فتح الشاشة.

### فشل الحفظ
- **Given:** قاعدة البيانات ترفض كتابة طرف من أطراف العملية.
- **When:** يحاول المستخدم تسجيل الدفعة.
- **Then:** لا يبقى أي أثر جزئي؛ تظهر رسالة داخل سياق الواجهة الحالي، يمكن إعادة المحاولة بأمان، ولا تنشأ دفعة مكررة.

### عزل المحطات
- **Given:** عميل وحركة تابعان لمحطة A ومستخدم في محطة B.
- **When:** يحاول المستخدم عرض السجل أو الدفع باستخدام معرف العميل مباشرة.
- **Then:** ترفض القراءة والكتابة حتى عند تجاوز الواجهة، ولا تُكشف تفاصيل السجل.

### التقرير
- **Given:** مجموعة حركات معلومة موزعة على فترة وصناديق وحالات مختلفة.
- **When:** يطبق المستخدم فلاتر التقرير ويصدره.
- **Then:** عدد الصفوف والمجموع يطابقان استعلام الحقيقة المعتمد، وتظهر الفلاتر والتواريخ والعملة في الملف.

### الترقية والنسخ
- **Given:** قاعدة نسخة سابقة تحتوي بيانات مترابطة.
- **When:** يتم تحديث التطبيق أو استعادة نسخة صالحة في بيئة الاختبار.
- **Then:** تنجح migration/restoration وتبقى الأرصدة والعلاقات والإعدادات صحيحة، أو يرفض الملف التالف دون تلف القاعدة الحالية.

## 11. استراتيجية الأتمتة والبوابة قبل التسليم

- تقارير تغطية واتجاهها، دون جعل النسبة وحدها معيار جودة.

### إصدار مرشح
- Regression كاملة على أكثر من API level وجهاز/كثافة.

### مؤشرات نجاح مقترحة

- كل migration مدعومة لها اختبار ترقية من قاعدة سابقة.
- لا crash أو ANR في جلسة smoke/regression المحددة.
- تغطية عالية للمنطق المالي والأمني؛ يحدد الفريق حداً واقعياً بعد قياس الوضع الحالي. لا تُغطّ النسبة على حساب جودة assertions.
- كل فشل اختبار قابل لإعادة الإنتاج مع خطوات وبيانات ثابتة.

## 12. أوامر تشغيل مبدئية (تحقق من أسماء المهام أولاً)

الأوامر التالية شائعة لمشاريع Android Gradle، لكنها لا تثبت أن كل task أو إعداد موجود في هذا المشروع. ابدأ بعرض المهام:

```bash
./gradlew tasks --all
```

ثم استخدم ما هو متاح فعلياً، مثلاً:

```bash
./gradlew test
./gradlew lint
./gradlew assembleDebug
./gradlew assembleRelease
./gradlew connectedAndroidTest
```

قد تكون المهام محددة بالموديول أو variant، مثل `:app:testDebugUnitTest` و`:app:lintDebug`؛ تحقق من `./gradlew :app:tasks --all`. لا تشغّل `connectedAndroidTest` إلا مع Emulator/جهاز اختبار متصل ومهيأ.

لفحص ملفات JavaScript داخل `<script>` في HTML يمكن استخراجها مؤقتاً وتشغيل `node --check` على كل مقطع؛ هذا فحص syntax فقط وليس اختبار DOM أو WebView أو business logic. توجد في السجل السابق عدة اختبارات bridge/regression مستقلة وقد نجحت 15/15 في نطاق سابق، لكن ذلك لا يعني أن المشروع بأكمله مغطى أو أن اختباراته تخص شاشة الديون.

إذا كانت اختبارات Node موجودة، افحص `package.json` وملفات scripts قبل اعتماد `npm test` أو `node ...test.js`. لا تفترض وجود npm test لمشروع Android لمجرد وجود Node في بيئة التطوير.

## 13. أنواع إضافية حسب الحاجة

- **اختبارات توافق API/العقود:** عند وجود خدمات خارجية أو بين واجهة JS وKotlin.
- **اختبارات دخان Smoke:** تحقق سريع بعد البناء والتثبيت من الإقلاع وتسجيل الدخول وفتح شاشة أساسية.
- **اختبارات صحة الإطلاق Sanity:** تحقق ضيق من التغيير المحدد بعد إصلاح عاجل.
- **اختبارات التوافق الرجعي:** بقاء بيانات المستخدم وتكامل الملفات بعد تحديث التطبيق.
- **اختبارات A/B أو قابلية الاستخدام:** فقط عند وجود تغيير تصميمي قابل للقياس وموافقة المنتج.
- **اختبارات الطفرات Mutation:** تعطل شرط/عامل حسابي عمداً في نسخة محلية لقياس قدرة الاختبارات على كشف الخطأ؛ لا تطبق على نسخة الإنتاج ولا تترك التغيير.
- **اختبارات Chaos/انقطاع:** قتل عملية أو قطع اتصال/مساحة في بيئة تجريبية لفحص التعافي، مع عزل تام عن بيانات الإنتاج.
- **اختبارات التوافق القانوني/الخصوصية:** مراجعة الاحتفاظ والموافقة والوصول والحذف وفق المتطلبات القانونية المحلية؛ هذه تحتاج صاحب صلاحية/مستشاراً مختصاً ولا تستنتجها الاختبارات التقنية وحدها.
