# تحليل إخفاقات اختبارات JavaScript الـ21

**المستودع:** `gbrhomidi/station-Abo_Ahmed2`  
**الفرع المفحوص:** `feature/ai-health-sqlite`  
**الالتزام:** `b5016d0b5c9eeed6708b9362d561adb211bc9cfb`  
**الهدف:** تحليل سبب فشل كل اختبار، التفريق بين خلل مرجح في التطبيق واختبار متقادم/غير مطابق، واقتراح العلاج والتحقق اللاحق.  
**حدود العمل:** تحليل للقراءة فقط؛ لم تعدل ملفات المشروع ولم يُجر أي تغيير أو دفع إلى GitHub.

> **تنبيه تفسيري:** عدد كبير من هذه الملفات اختبارات ساكنة تبحث عن أسماء أو نصوص محددة في المصدر، وليست اختبارات تشغيل حقيقية. فشل assertion نصي لا يثبت وحده وجود عطل وظيفي؛ لكنه قد يكشف عقداً غير متوافق أو فجوة تحتاج اختباراً تشغيلياً. لذلك صنّفت الحالات بحذر، وذكرت المواضع التي تحتاج مراجعة متطلب المنتج قبل القرار.

## خلاصة تنفيذية

من بين الإخفاقات الـ21:

- **غالبية النتائج مرجح أنها false positives أو اختبارات قديمة/مفرطة الصرامة:** الفحص يطلب أسماء دوال أو تعليقات أو صياغة JavaScript حرفية، بينما التطبيق ينفذ المسار بأسماء أو helpers أو تنسيق مختلف.
- **حالات يُرجّح فيها نقص تطبيق إذا كان المتطلب المعلن شاملاً:** رابط `theme.css` غائب عن ثلاث صفحات، والحارس المشترك للمودالات غير مضمّن مباشرة في 12 شاشة. ينبغي مراجعة الاستثناءات والمتطلب قبل إدخال التغيير.
- **حالة ذات عدم توافق تطبيقي أوضح:** كود `report-drilldown.js` يحفظ الحمولة في `sessionStorage` ثم ينتقل بلا معاملات URL، بينما `reports-drilldown.html` يقرأ المعاملات من URL. هذا يستدعي اختباراً طرفاً لطرف قبل تغييره.
- **حالة محتملة في توصيل Source Trace:** توجد وظيفة evidence في قاعدة البيانات، لكن واجهة/جسر الاستثناءات واسم drilldown المطلوبين في الاختبار لا يظهران بالاسم المتوقع. يحتاج ذلك إلى حسم عقد API.
- **لم تُنفذ اختبارات متابعة سلوكية أثناء هذا التحليل**؛ التوصيات أدناه ليست ادعاءً بنتائج جديدة.

## أنماط مشتركة وحلول على مستوى مجموعة الاختبارات

1. **تقليل الفحوصات المرتبطة بنص حرفي:** أسماء الوظائف، ترتيب الشيفرة، التعليقات المرقمة وتقسيم الأسطر ليست عادةً عقداً عاماً. الأفضل تحليل AST أو اختبار الوظائف والسلوك.
2. **تحديد نطاق الصفحة/الوحدة الصحيح:** اختبر `dashboard.html` للوحة التحكم، ولا تفرض اعتماداً واحداً على كل تقارير HTML إذا كان بعضها self-contained.
3. **إنشاء اختبارات عقد حقيقية بين الطبقات:** WebView → Android Bridge → DatabaseHelper → SQLite، مع تحقق من payload والنتيجة والآثار الجانبية.
4. **تمييز الاختبار الفاشل عن خلل المنتج:** اطلب شواهد تشغيلية (قيمة محفوظة، تقرير، callback، سجل) قبل تصنيف false positive أو bug.
5. **تثبيت متطلبات التقارير:** وثق لكل شاشة methods والمرشحات وحالة المصدر والصفحات وقراءات العدادات والتصدير، وحدود العرض المقبولة.
6. **إعادة تشغيل الاختبارات بعد تحديثها:** تحديث الاختبار لا يعني نجاح التطبيق؛ يجب تشغيل نسخة الاختبار المنقحة ثم اختبارات التكامل وUI المناسبة.

- **أولوية عالية للتحقق:** مسار drilldown/Source Trace بسبب احتمال عدم تطابق sessionStorage مع مدخلات URL، وكذلك توفر bridge للاستثناءات المطلوبة.
